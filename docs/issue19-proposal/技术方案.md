# ProcessTopMonitor（暂名）技术方案 —— 进程资源排行悬浮窗插件

> 对应 issue：deYangar/ProcessNetMonitor#19
> 定位：**独立的新 TrafficMonitor 插件**（issue 评论已拍板：ProcessNetMonitor 专注进程流速，本插件专注资源占用排行，两者同形式并存）
> 日期：2026-10-25 ｜ 状态：方案稿，待评审，未编写实现代码

---

## 0. 背景与目标

issue #19 中用户希望获得「同当前样式」的 **CPU Top 10 悬浮窗**，停靠在流速悬浮窗旁边。作者已回复将另起一个同形式插件。本方案将其扩展为一台机器上最常用的五类资源维度的进程排行：

| 维度 | 排行依据 | 单位 |
|---|---|---|
| CPU | CPU 占用率 | % |
| 内存 | 专用提交内存（可选工作集） | MB/GB |
| 磁盘 IO | 读写传输速率 | MB/s |
| GPU | 引擎利用率 | % |
| 显存 | 专用显存占用（可选+共享） | MB |

产品原则（继承 PNM）：

- 悬浮窗观感与 PNM 悬浮信息窗一致（亚克力/圆角/进程图标/右对齐数值/深浅主题自动）
- 零第三方依赖、`/MT` 静态 CRT、单 DLL 双架构（x64/x86）、普通用户权限即可运行
- 自身开销目标：常驻 CPU < 1%、私有内存 < 10MB（任务管理器常驻约 30~80MB，本插件量级应明显低于它）
- Win7 ~ Win11 全兼容（GPU 维度按系统版本降级，见 §2.4/§10）

## 1. 功能范围

### 1.1 核心功能

1. **排行悬浮窗**：显示某一指标的 Top N（默认 10，可配 5/10/15）进程列表。每行 = 进程图标 + 进程名 + 数值（右对齐，同 PNM 悬浮窗布局）。同名多进程（Chrome 等）默认合并为一行，可展开显示子进程（展开能力为 v2，见 §11）。
2. **指标集合**：CPU / 内存 / 磁盘 IO / GPU / 显存，共 5 个维度。磁盘 IO 可细分「读速率 / 写速率」两个子视图；显存可细分「专用 / 共享」。
3. **两种窗口模式**（详见 §6）：
   - 单窗切换模式：一个悬浮窗内通过滚轮/点击/快捷键切换当前显示的指标；
   - 多窗模式：自定义同时打开多个悬浮窗，每个窗口各自绑定一个指标、独立位置独立主题。
4. **窗口联动停靠**（详见 §7）：检测到 PNM 详情窗 / TM 主悬浮窗存在时，插件窗口默认停靠在其旁边，并跟随移动；用户手动拖离后解除。
5. **任务栏显示项**（可选，建议提供）：一个 IPluginItem，在 TM 任务栏/主窗显示当前 CPU Top1 进程名 + 占用（形式同 PNM 的 Up/Down 两行项），点击切换悬浮窗显隐——给 TM 一个原生集成入口，也复用 PNM 已验证的 item 交互模式。
6. **标题栏摘要**：悬浮窗头部显示该维度的系统总量（如 CPU 总占用、内存总量/已用、GPU 总占用），与 Top 列表互相印证。

### 1.2 明确不做（首版）

- 网络流量排行（PNM 的领域，不重复建设）
- 历史/趋势图（PNM 有完整 history 体系，本插件 v2 再评估）
- 结束进程等危险操作（首版仅「定位文件 / 属性」；PNM 有现成实现，v2 可搬）
- CPU 温度、频率等传感器指标（TM 主程序已提供）

## 2. 数据获取调研（Windows）

TrafficMonitor 及其插件宿主仅存在于 Windows，因此「不同平台」在本方案中落实为 **Windows 版本维度**（Win7/8/8.1/10/11、x86/x64/WOW64、WDDM 版本、有无独显、RDP 会话）。macOS/Linux 无对应宿主，不展开（其等价物为 `top`/`psutil`，仅备注一句）。

### 2.1 CPU —— 推荐单一快照法

**候选方案对比**：

| 方案 | API | 开销 | 限制 |
|---|---|---|---|
| **系统快照（推荐）** | `NtQuerySystemInformation(SystemProcessInformation)` | 一次调用返回全部进程，300 进程实测毫秒级（1~5ms） | ntdll 未公开 API，需动态取函数指针；结构体自行定义 |
| 逐进程句柄 | `OpenProcess` + `GetProcessTimes` | O(n) 次 OpenProcess，句柄开销大 | 受保护进程（杀软等）打开失败或数据缺失；短命进程易漏 |
| PDH 计数器 | `PdhOpenQuery("\Process(*)\% Processor Time")` | 首次枚举 + 每次 collect 数十 ms | 实例名撞名加后缀（#1/#2）需处理；最慢 |
| Toolhelp32 快照 | `CreateToolhelp32Snapshot` | 快 | 只有进程列表，**没有 CPU 时间**，需配合其他 API |

**推荐路线**：`NtQuerySystemInformation(SystemProcessInformation)`——任务管理器进程列表同源数据。一次调用同时拿到：

- 每进程 `KernelTime`/`UserTime`（CPU 时间，累计值）
- `ReadTransferCount`/`WriteTransferCount`/`OtherTransferCount`（IO 计数，见 §2.3）
- `WorkingSetSize`/`PrivatePageCount`（内存，见 §2.2）
- 进程名（ImageName，NT 路径）、PID、线程数、基优先级

**CPU% 计算**：`(ΔKernelTime + ΔUserTime) / (ΔwallTime × LogicalProcessorCount) × 100`，逻辑核数取 `GetLogicalProcessorInformation(Ex)`。CPU 时间是系统启动以来的累计值，天然免疫采样间隔抖动；首拍无差值显示 `--`。

**风险与对策**：

- **WOW64 结构对齐**：x86 插件跑在 x64 系统上时，wow64 层会返回 32 位视图的 `SYSTEM_PROCESS_INFORMATION`（`SYSTEM_THREAD::StartAddress` 为 `ULONG_PTR`），结构定义中所有指针宽度字段用 `ULONG_PTR` 并按 `NextEntryOffset` 步进即可（Process Hacker 同款处理，成熟方案）。x64 原生无此问题。PNM 的 win7_compat_check 双架构测试工具直接复用来验证。
- **未公开 API 稳定性**：该结构自 NT4 起稳定，任务管理器/Process Explorer/Process Hacker 全在用；仍按「尾部字段不解析」原则只读需要的字段，缓冲区按返回长度 `StatusInfoLengthMismatch` 递增重试分配（初始 512KB，翻倍增长）。
- **受保护进程**：快照中仍有 CPU 时间，ImageName 可能为空 → 显示 `<PID>`，与 PNM「进程名永不过期」策略一致做名字缓存兜底。
- **系统级空闲进程**：`Idle`/`System Idle Process` 不参与排行，但计入标题栏系统总量（100% − idle%）。

### 2.2 内存 —— 同一快照，零额外开销

`SYSTEM_PROCESS_INFORMATION` 中直接可取：

| 字段 | 口径 | 对应任务管理器列 |
|---|---|---|
| `PrivatePageCount` | 专用提交内存（**默认口径**） | 详细信息页「提交大小」 |
| `WorkingSetSize` | 工作集（含共享页） | 进程页「内存(活动的专用工作集)」的近似 |

- 排行默认按**专用提交**（更能反映进程真实负担，不受共享库重复计入影响）；设置中可切换工作集口径。
- 快照法拿不到「专用工作集」（private working set）精确值（需 `GetPerformanceInfo`/PSA 计数器），方案不追这个口径，设置页注明差异即可。
- 同名进程合并时内存直接求和（各进程独立地址空间，求和正确）。
- **瞬时值无 delta**，首拍即可显示——CPU/IO 需要两拍，内存不需要，首拍体验更好。

### 2.3 磁盘 IO —— 同一快照的 IO 计数，口径必须讲清

**推荐路线**：快照内嵌的 `IO_COUNTERS`（`ReadTransferCount`/`WriteTransferCount` 累计值）做差 → 读写速率。

**关键口径事实**（微软文档 + Microsoft Q&A 证实）：`GetProcessIoCounters` 及快照 IO 计数统计的是进程**全部句柄 IO**（文件 + **网络 socket** + 设备），**没有磁盘/网络拆分**。socket 收发同样计入 Read/Write TransferCount。任务管理器的「磁盘」列与此同源同口径。

**结论与对策**：

- 默认口径：**读+写传输速率**，工具提示中注明「与任务管理器磁盘列同口径，含少量网络 IO」。对绝大多数进程网络 IO 占比可忽略；高网络进程（下载器/浏览器）数值会偏高，属口径已知行为，不是缺陷。
- 精确拆分（仅文件/磁盘 IO）唯一通用方案是 **ETW FileIo/DiskIo 事件**：项目已有完整 ETW 基建经验（etw_capture.cpp：会话管理、TDH 解析、占用降载），但文件 IO 事件流量远大于 TCP/UDP 事件（每次 NtWriteFile 一条），持续追踪的开销与本插件「轻量常驻」定位冲突 → **列为 v2 高级选项**（默认关闭），首版不做。
- 展示：默认「读写合计 MB/s」单列；设置可切「读 / 写」分列子视图（同一数据，无需额外采集）。

### 2.4 GPU —— PDH 性能计数器主线（Win10 1709+）

**候选方案对比**：

| 方案 | API/来源 | 最低版本 | 开销 | 限制 |
|---|---|---|---|---|
| **PDH GPU Engine（推荐）** | `\GPU Engine(*)\Utilization Percentage` | **Win10 1709** | 实例数 = 进程数×引擎数（数百~上千），单次 collect+格式化约 2~20ms，1s 一次可接受 | 实例路径字符串解析是主要成本；引擎并行求和可 >100% 需定口径 |
| D3DKMT 统计 | `D3DKMTQueryStatistics`（gdi32 动态加载，任务管理器同款） | Vista+（语义随 WDDM 演进） | 进程×适配器次内核调用 | 需要 `D3DKMTEnumAdapters` 枚举 LUID；NodeRunningTime 为累计值需自行 delta；Win7/8 上 per-process 语义未验证 |
| NVML | nvml.dll | N 卡专属 | 低 | **仅覆盖 NVIDIA + 主要是 CUDA 进程**（图形进程显存/利用率覆盖不全），非通用，不做主线 |
| IGCL/ADLX | Intel/AMD SDK | 厂商专属 | — | 非通用、引入闭源依赖，违背零依赖原则，排除 |

**推荐路线**：PDH `GPU Engine` 计数器。

- 实例名格式 `pid_1234_luid_0x..._phys_0_eng_0_engtype_3D`：按 `pid_` 前缀解析出 PID 分组，对该进程全部引擎实例的 `Utilization Percentage` 求和。
- **口径**：默认「全部引擎求和，上限 100%」（任务管理器默认视图同法）；设置可切「仅 3D 引擎」（engtype_3D，游戏场景更直观）。多 GPU 场景默认全部物理适配器合计，设置可按适配器分列（v2）。
- 采样需要**两次 collect**（该计数器类型为区间型，`PdhGetFormattedCounter` 自动用两拍差值 cook），因此 GPU 首拍同样显示 `--`。
- **PDH 查询单独建、单独降频**：与系统快照分开（默认 1s vs 500ms），关闭 GPU 相关窗口时整个 PDH 查询关闭（`PdhCloseQuery`），零残留开销。

**降级链**：Win10 1709 以下 / 无 GPU / 计数器不存在（RDP 会话下 WDDM 虚拟化常返回空数据）→ 该维度从指标列表中隐藏，设置页显示原因说明。Win7/8 若将来需求强烈，D3DKMTQueryStatistics 是唯一路线，列为远期备选（首版不做，未验证不承诺）。

### 2.5 显存 —— PDH GPU Process Memory（Win10 1709+）

- 计数器：`\GPU Process Memory(*)\Local Usage`（专用显存，新版本 build 名为 Dedicated Usage，按计数器类别名枚举两种都兼容）与 `Shared Usage`（共享系统内存）。
- 实例名同样以 `pid_N_...` 开头，解析逻辑与 GPU Engine 共用。
- 默认排行按**专用显存**；设置可切「专用+共享」合计视图。瞬时值，无需 delta。
- 多 GPU：默认合计，可按适配器分列（v2）。
- 降级链与 GPU 相同（1709 以下隐藏维度）。

### 2.6 汇总：采集矩阵

| 指标 | API | 版本要求 | 默认频率 | 单次开销 | 首拍可用 |
|---|---|---|---|---|---|
| CPU | NtQuerySystemInformation 快照 | Win7+ | 500ms | 1~5ms | 否（需两拍） |
| 内存 | 同上快照内字段 | Win7+ | 随快照 | 0（附带） | **是** |
| 磁盘 IO | 同上快照 IO_COUNTERS | Win7+ | 随快照 | 0（附带） | 否（需两拍） |
| GPU | PDH GPU Engine | Win10 1709+ | 1000ms | 2~20ms | 否（需两拍） |
| 显存 | PDH GPU Process Memory | Win10 1709+ | 随 GPU 查询 | 1~5ms | **是** |

普通用户权限全覆盖；无需管理员；全部动态加载（ntdll / pdh / gdi32），无新链接依赖。

### 3.5 PNM 侧的配合改动（可选，建议做）

PNM 两个窗口的类名带实例指针后缀（`PNMDetail_%p`、`PNMTooltip_%p`），窗口标题悬浮窗为空、详情窗为 `"ProcessNetMonitor"`——跨进程精确 `FindWindow` 只有详情窗可行。两个选项：

- **A（零改动，本方案默认）**：新插件用「类名前缀匹配（`PNMDetail_`）+ 所属进程为 TrafficMonitor.exe」双条件 EnumWindows 检测。前缀稳定，可靠。
- **B（PNM v1.19+ 顺手改）**：类名去 `%p` 后缀固化为常量（PNM 两窗口本就是单例，后缀属过度防御）。改后检测更干净，也方便未来其他联动。

建议 B 作为 PNM 下个小版本的顺手改动，A 保证新插件不依赖 PNM 版本。

## 4. 总体架构设计

```
┌────────────────────────────────────────────────────────────────┐
│                    ProcessTopMonitor.dll                        │
│                                                                  │
│  ┌──────────────┐   快照/排行数据   ┌──────────────────────┐    │
│  │ metrics_     │──(m_data_lock)──▶│ CTopListWindow × N    │    │
│  │ collector    │   PostMessage     │ (UI 线程=TM 主线程)   │    │
│  │ (定时器线程)  │   WM_PTM_REFRESH  │  ├ 指标绑定/切换      │    │
│  │  ├ sys快照   │                   │  ├ ULW 视觉管线       │    │
│  │  └ PDH查询   │                   │  └ 图标分帧提取       │    │
│  └──────┬───────┘                   └──────────┬───────────┘    │
│         │ delta/排序                            │                │
│  ┌──────▼───────┐                   ┌──────────▼───────────┐    │
│  │ top_         │                   │ dock_manager          │    │
│  │ aggregator   │                   │ (EnumWindows 探测 +   │    │
│  └──────────────┘                   │  WinEventHook 跟随)   │    │
│                                     └──────────────────────┘    │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ plugin_main：ITMPlugin 实现 / IPluginItem / InitOnce      │   │
│  │ 设置持久化(settings.json) / i18n / 崩溃防护 / 选项对话框    │   │
│  └──────────────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────────────┘
        │ 宿主接口                          │ 跨进程探测
        ▼                                  ▼
  TrafficMonitor.exe              PNM 详情窗 / TM 主悬浮窗
```

**线程模型**（继承 PNM 已验证模型，不发明新的）：

| 线程 | 职责 | 纪律 |
|---|---|---|
| TM 主线程 | 全部窗口（含 N 个悬浮窗）的消息循环与绘制、任务栏 item 绘制、选项对话框 | 窗口成员只有此线程可碰 |
| TimerQueue 定时器线程 | metrics_collector 采集 + aggregator 排序 + 缓存写入 + PostMessage 通知 | `m_refresh_busy` CAS 防重入；不碰任何窗口成员；所有共享数据进 `m_data_lock` |
| （无新增线程） | 图标提取由 UI 线程 OnPaint 末尾分帧驱动，不建后台线程 | — |

**关键设计决策**：

1. **单一数据管线服务全部窗口**：无论 1 个窗还是 5 个窗，采集定时器只有一套；每拍产出「全部已启用指标的 Top N 结果表」，各窗口按绑定指标自取。多开窗口不增加采集成本（同指标共享），这是多窗模式的性能前提。
2. **按需启停采集维度**：collector 维护「当前被至少一个可见窗口绑定的指标集合」。GPU 系列无窗口绑定时 `PdhCloseQuery` 全关；全部窗口隐藏时整个定时器停（任务栏 item 所需数据降级为 TM tick 时惰性采一拍）。
3. **窗口类多实例化**：PNM 的 `s_instance` 单例模式改为 `HWND → CTopListWindow*`（`SetWindowLongPtrW(GWLP_USERDATA)` + 静态注册表兜底），WndProc 静态分发。
4. **崩溃防护先行**：§3.1 的防护机制在第一个窗口创建前就位（PNM issue #7 的事故不重演）。

## 5. 数据流设计

### 5.1 一拍采样周期（默认 500ms tick，GPU 每 2 tick 一次）

```
TimerQueueTimer 线程（RefreshTick，CAS 防重入）
 1. CheckLanguageChange()                        // 复用 PNM
 2. [每拍] NtQuerySystemInformation 快照
      ├─ 解析出 vector<RawProc>{pid, name, cpu_time, io_r, io_w, ws, private}
      ├─ 与上拍差值 → cpu%、io_read_Bps、io_write_Bps（计数器回绕/回退钳 0）
      └─ 上拍状态整体替换（进程退出自然淘汰，无需显式清理）
 3. [每 2 拍,若 GPU 已启用] PdhCollectQueryData ×2 → GPU%/VRAM per pid
      └─ 实例路径解析：pid→(引擎利用率之和, LocalUsage, SharedUsage)
 4. top_aggregator：
      ├─ 按指标分别聚合：同名进程合并（求和）、排序、截 Top N
      ├─ 产出 Snapshot{ per-metric TopRows[5维], 系统总量摘要 }
      └─ （可选）数值 EMA 平滑，抑制排行抖动
 5. EnterCriticalSection(m_data_lock)
      m_snapshot = std::move(snapshot)           // 整体替换，无部分状态
    Leave
 6. 对每个可见窗口 PostMessage(hwnd, WM_PTM_REFRESH, metric_hint, 0)
    （不可见窗口不发——隐藏窗口不重绘，自然省 CPU）
 7. 任务栏 item 数据从 m_snapshot 取（DataRequired/TM tick 时，不重复采集）
```

### 5.2 窗口侧（UI 线程）

```
WM_PTM_REFRESH:
 1. 锁内拷贝自己绑定指标的 TopRows（浅拷贝 POD 行，微秒级）
 2. 脏检查：名单（PID 序列）+ 数值量化（保留 1 位小数/MB 取整）比对上拍
    → 完全相同则直接 return（0 重绘 0 合成，静止画面零成本）
 3. 有变化 → 重建 ULW 表面内容（ComposeLayeredSurface）+ 图标 miss 入队
    OnPaint 末尾 PumpIconExtraction(2) + 若有补齐则 Invalidate 自驱动
```

### 5.3 与 PNM 数据流的差异点

| PNM | 本插件 |
|---|---|
| ETW 事件驱动的累计字节 → 滚动 1s 窗口速度 | 系统计数器快照 → 相邻两拍差分（无需滚动窗口） |
| 单一悬浮窗 + 单一详情窗 | N 个排行窗共享一份快照 |
| 采集器有「ETW 主/传统备」双后端切换 | 单后端，但维度有启停（GPU 系列整组开关） |

## 6. 悬浮窗模式设计

### 6.1 窗口外观

复刻 PNM 悬浮信息窗：宽约 300px（DPI 自适应）、`WS_POPUP + WS_EX_TOPMOST + WS_EX_TOOLWINDOW`（常驻窗加 `WS_EX_APPWINDOW`，给任务栏按钮与最小化恢复入口——issue #18 教训）、亚克力/透明/模糊/不透明四档效果 + 不透明度滑条、圆角、深浅主题自动 + 文字反色。布局：

```
┌──────────────────────────┐
│ CPU            ▾  [—][×] │  ← 标题栏：当前指标（点击弹指标菜单）
│ 总占用 23%  8/16 核活跃    │  ← 摘要行（该维度系统总量）
│ 1 chrome.exe       6.2%  │
│ 2 Code.exe         4.8%  │  ← Top N 行：图标+名+数值（右对齐）
│ 3 ...                     │
│ 10 ...                    │
└──────────────────────────┘
```

### 6.2 单窗切换模式（默认）

- **切换方式**：滚轮（上下循环）、点击标题栏「指标名」弹菜单、快捷键 `1~5`；切换动画只重绘不位移。
- 指标顺序固定：CPU → 内存 → 磁盘 IO → GPU → 显存（不可用维度灰显并标注原因）。
- 切换只影响本窗读取的快照子集，**不触发额外采集**（快照每拍本来就含全部启用维度——见 §4 决策 1，切换零延迟）。
- 每「窗+指标」记住独立状态无必要，单窗模式共享一份排序与设置。

### 6.3 多窗模式

- **入口**：窗口标题栏右键菜单 / 托盘菜单 / 选项对话框 →「新建悬浮窗」→ 弹出指标选择 → 创建绑定该指标的新窗。
- **每窗独立**：指标绑定、位置、尺寸（行数多时允许拉高）、主题档、透明效果。同一指标允许开第二窗（如「磁盘读」+「磁盘写」两窗）。
- **上限**：建议 6 个（5 指标 + 1 冗余），超限提示（每窗一个 ULW 表面 + 模糊层，6 窗约 6×(300×600×4B×2) ≈ 8MB 显存级，可控但没必要更多）。
- **实现**：`CTopListWindow` 多实例（§4 决策 3）；窗口标题区分（如 "PTM-CPU"）便于 Win32 级识别与调试。
- **关闭语义**：关单个窗 = 移除该窗配置；关全部窗 = 退出悬浮窗模式（任务栏 item 保留，可随时重开）。

### 6.4 持久化 schema（settings.json）

```json
{
  "refresh_ms": 500,
  "default_topn": 10,
  "memory_basis": "private",        // private | workingset
  "gpu_basis": "all_engines",       // all_engines | 3d_only
  "io_view": "combined",            // combined | read | write
  "vram_basis": "dedicated",        // dedicated | dedicated_shared
  "window_mode": "single",          // single | multi
  "windows": [                       // 多窗模式：每窗一项；单窗模式仅 [0]
    { "metric": "cpu", "x": 100, "y": 100, "w": 300, "h": 420,

  ],
  "color_mode": 0, "popup_effect": 0, "popup_opacity": 100,
  "lang": "auto", "debug_logs": false
}
```

运行期变更即时写盘（同 PNM：WM_EXITSIZEMOVE / 设置变更时机落盘，避免每拍写盘）。

## 7. 窗口联动停靠设计

### 7.1 停靠目标与优先级

| 优先级 | 目标 | 检测方式 | 说明 |
|---|---|---|---|
| 1 | **PNM 详情窗**（类名前缀 `PNMDetail_`，标题 `ProcessNetMonitor`，常驻） | EnumWindows：类名前缀 + `GetWindowThreadProcessId` 属 TrafficMonitor.exe + `IsWindowVisible` | 最理想的常驻锚：常显、可拖动、与流速信息同屏 |
| 2 | **TM 主悬浮窗**（类名前缀 `TrafficMonitor`，桌面浮动） | 复用 PNM 的 `IsTMMainWindow` 判定逻辑（类名 + 与任务栏位置关系） | 无 PNM 详情窗时的锚 |
| 3 | PNM hover 悬浮窗（类名前缀 `PNMTooltip_`） | 同前缀法 | **不作锚**：生命周期为秒级（hover 才出现），跟随它会反复吸附加释放；仅用于「存在性提示」——检测到 PNM 悬浮窗体系在用时，新窗首显位置向其侧偏 |

### 7.2 停靠状态机（每窗独立）

```
[Floating 独立浮动] --检测到锚窗 & !manual_moved--> [Docked 停靠跟随]
[Docked] --用户拖离(WM_EXITSIZEMOVE 后距锚 > 阈值)--> [Detached 手动脱离]
[Detached] --右键菜单「重新停靠」/ 重启--> [Docked]
[Docked] --锚窗消失(关闭)--> [Floating 冻结原位]（锚重现不自动吸回，避免窗口跳动；菜单可手动重新停靠）
```

- **默认停靠边**：锚窗右侧、垂直顶对齐；右侧出屏则翻到左侧（`PNM_GetWorkAreaForRect` 工作区翻转逻辑复用）。
- **多窗排布**：停靠态的多窗按创建序横向级联（窗 i 停在窗 i-1 右侧），一行放不下自动换行到锚窗下方。
- 「默认停靠」语义 = **首显时若锚存在则贴过去**；用户拖离后尊重用户位置（`manual_moved` 持久化，重启保持）。

### 7.3 跟随机制：WinEventHook（跨进程的正确答案）

PNM 的子类化跟随（`SetWindowLongPtrW` 拦 `WM_WINDOWPOSCHANGED`）**只能用于同进程窗口**，对 PNM/TM 的窗口跨进程不可用。替代：

- **主线**：`SetWinEventHook(EVENT_OBJECT_LOCATIONCHANGE, EVENT_OBJECT_LOCATIONCHANGE, 0, 回调, TrafficMonitorPID, 0, WINEVENT_OUTOFCONTEXT)` ——按锚窗所属进程 ID 过滤，系统只在目标进程窗口位移时投递事件到本插件（安装钩子时设置的线程消息循环），事件驱动、零轮询成本、系统原生支持跨进程。回调内仅记录新矩形 + 向 UI 线程 PostMessage 重定位（不在回调里做重活——回调跑在安装线程，PNM「持锁路径不做重活」铁律同款纪律）。
- **跟随策略复用 PNM 三段式**：纯位移走轻量 delta（直接 `SetWindowPos` 同偏移量）；尺寸变化/跨显示器走节流全量重定位（150ms）；拖动结束（`EVENT_SYSTEM_MOVESIZEEND`）强制终判。
- **兜底轮询**：500ms `GetWindowRect(锚)` 比对（WinEventHook 被安全软件干扰或漏事件时保底——PNM「子类化被剥退回轮询」的同款防御哲学；注意这是**失败可见**的兜底，不是缺陷遮羞布）。
- **生命周期**：全部窗口处于 Docked 才挂 hook；全部 Detached/Floating 时 `UnhookWinEvent`。锚进程退出（TM 关闭）钩子自动失效，配合状态机回 Floating。
- **锚切换**：锚优先级变化（详情窗开/关）时重挂（换 pid 过滤参数），重挂失败不致命（轮询兜底在）。

## 8. 性能设计（具体措施）

### 8.1 采集侧

1. **一拍三指标**：CPU/内存/IO 共享一次 `NtQuerySystemInformation`（§2.6），比任务管理器逐进程查询更省；快照缓冲区按需增长后**复用不释放**（避免每拍 512KB 分配）。
2. **频率分层**：快照 500ms（默认，可配 250/500/1000/2000ms，同 PNM 档位习惯）；GPU PDH 1000ms 且**倍频于快照 tick**（每 2 拍一次，单一定时器分频，不建第二个定时器）。
3. **按需启停**（§4 决策 2）：无 GPU 窗口 → PDH 全关；全部窗口隐藏 → 采集定时器删除；重开窗口时按需重建（建查询首次 ~10ms，一次性成本）。任务栏 item 单独存在时维持 1s 低频拍（TM tick 驱动即可满足）。
4. **PDH 实例解析成本控制**：GPU 实例路径的字符串解析（wcstok 拆 pid）是主要 CPU 成本。优化：维护「实例路径 → (pid, 引擎类型)」缓存表，`PdhEnumObjectItems` 发现实例集合未变时直接用缓存映射；只解析关心的计数器（Utilization Percentage / Local Usage / Shared Usage 三个），不碰 Running Time 等其余计数器。
5. **delta 钳制**：计数器回退（PID 复用、系统会话切换）差值钳 0，防 uint64 下撑出天文数字（PNM ComputeWindowSpeeds 同款防御）。

### 8.2 渲染侧

6. **脏检查跳过重绘**：Top N 名单与量化数值未变 → 不重建 ULW 表面、不 Invalidate（静止画面零 GPU/CPU；排行数据量化后实际变化频率远低于采样频率）。
7. **ULW 表面复用**：窗口尺寸不变时 DIB 表面不重建（PNM `EnsureLayeredSurface` 同款）；内容层 + coverage 双底 + 采样三表面常驻复用。
8. **图标分帧提取**：绘制只查缓存，磁盘提取每帧 ≤2 个（PNM 验证过的模式）；图标缓存无上限问题（进程图标种类有限），但 PID 复用下按 exe 路径缓存天然去重。
9. **数值格式化缓存**：格式化结果字符串随脏检查一起比对，未变不重新 swprintf。

### 8.3 停靠侧

10. WinEventHook 事件驱动（无轮询常开）；回调只记矩形+PostMessage。
11. 兜底轮询仅在 Docked 态存在，500ms 一次 `GetWindowRect`（微秒级系统调用）。

### 8.4 预算表（验收口径）

| 场景 | 目标 |
|---|---|
| 1 窗（CPU 单指标），500ms 拍 | 插件进程 CPU < 0.3%，私有内存 < 8MB |
| 5 窗全指标（含 GPU PDH 1s） | CPU < 1%，私有内存 < 12MB |
| 全部窗口隐藏 | CPU ≈ 0%（定时器已停），内存 < 4MB |
| 静止画面（数据无变化） | 0 重绘、0 合成 |
| 拖动锚窗跟随 | 插件自身不增加可感知延迟（delta 路径 < 1ms/事件） |

验收工具复用项目模式：harness 程序 + 截图比对（tools/verify_* 的做法平移到新仓库）。

## 10. 兼容性与风险清单

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | Win10 1709 以下无 GPU/显存计数器 | 维度缺失 | 主动检测（`PdhEnumObjects` 查类别存在）→ 隐藏维度 + 设置页注明；不做半可用状态 |

| 6 | PDH 实例名格式随 Windows 更新变化（历史发生过 engtype 命名调整） | GPU 数据缺失 | 解析宽松化（pid_ 前缀必配，其余字段尽力解析）；解析失败样本计入调试日志 |
| 7 | 受保护进程（PPL）名字空 | 显示 `<PID>` | 进程名缓存兜底（PNM v1.11 策略）+ 首拍接受空名 |
| 8 | 短命进程闪现闪退导致排行跳动 | 观感 | 排行场景**允许自然消失**（与 PNM「永不消失」策略不同——排行是瞬时视图，保留僵尸行反而误导）；EMA 平滑可选开启 |
| 9 | 跨进程跟随钩子被安全软件拦截 | 停靠跟随失效 | WinEventHook 是系统公开 API（放大镜/读屏器同用），风险低；轮询兜底保可用 |
| 10 | 锚窗（PNM 详情窗）类名变更/未装 PNM | 检测不到 | 检测为能力探测而非依赖：找不到锚即独立浮动，功能完整可用；前缀匹配失败静默降级 |
| 11 | TM 宿主线程差异（1.85/1.86 DataRequired 线程不定） | 初始化时序问题 | InitOnce 双入口 + 窗口创建确保在主线程（PNM issue #12 教训整套复用） |
| 12 | DLL 卸载期窗口销毁崩溃 | 宿主 TM 崩溃 | g_shutting_down + SafeDestroyWindow + SEH（issue #7 方案整套复用） |
| 13 | 多窗 + 亚克力多层表面的显存占用 | 低配机负担 | 窗口数上限 6；透明效果档可整体降为不透明 |
| 14 | ntdll 未公开结构未来变动 | 极端情况下 CPU/IO 数据异常 | 只读头部稳定字段；解析带防御性长度校验；异常时显示采集失败而非崩溃 |

## 11. 实施阶段建议

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **M1 核心可用** | 插件骨架（接口/i18n/崩溃防护/构建）+ collector 快照路线 + CPU/内存/IO 三维度 + 单窗（固定指标每窗一个，先不做切换）+ 设置持久化 | 任务管理器对照 CPU%/内存值一致（±1%）；三窗同开 CPU < 1%；Win7/x64/x86 三环境跑通 |
| **M2 GPU + 切换** | PDH GPU/显存 + 降级链 + 单窗指标切换交互 + 任务栏 item（CPU Top1） | 与任务管理器 GPU 页对照；Win7 上维度正确隐藏；切换无闪烁 |
| **M3 多窗 + 停靠** | window_manager 多实例 + windows[] 持久化 + dock_manager（检测/WinEventHook/状态机）+ 新建窗菜单 | 停靠 PNM 详情窗旁并跟随拖动（不掉队）；拖离解除；重启恢复全部窗口 |
| **v2 候选**（不承诺） | ETW 精确磁盘 IO 档、行展开子进程、详情表格模式、历史趋势、签名分类列、按适配器分列 GPU | — |

每个阶段结束跑一次 harness 截图验收 + 双架构构建（win7_compat_check），发布节奏照 PNM 惯例（release notes + 版本号独立演进）。

## 12. 待拍板问题

1. **插件名**：暂用 `ProcessTopMonitor`（与 ProcessNetMonitor 对仗）；备选 `ProcessResMonitor` / `TopMon`。仓库独立新建。
2. **任务栏 item**：是否首版提供（建议提供 1 个「CPU Top1」item，复用 PNM 的 item 自绘与点击交互模式，工作量小、入口价值大）。
3. **磁盘 IO 列名**：直接叫「磁盘 IO」并注明口径，还是叫「IO 速率」更严谨？
4. **GPU 口径默认值**：「全部引擎求和」对游戏场景常显示 100%+ 截断，是否默认「仅 3D」？（建议默认全部引擎求和——与任务管理器一致，争议最小）
5. **停靠默认开启**：默认自动停靠 PNM 详情窗（建议开），还是默认独立浮动、停靠仅作为菜单选项？
6. **PNM 侧配合改动**（§3.5 选项 B，类名固化）是否排进 PNM 下个小版本。
