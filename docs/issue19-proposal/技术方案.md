# ProcessTopMonitor 技术方案 —— 进程资源排行悬浮窗插件

> 对应 issue：deYangar/ProcessNetMonitor#19
> 定位：**独立的 TrafficMonitor 插件**（ProcessNetMonitor 专注进程流速，本插件专注资源占用排行，两者同形式并存）
> 日期：2026-10-25 ｜ 状态：**v2（2026-10-25 拍板落实版）**
> v1 → v2 变更：磁盘 IO 首版即 ETW 精确口径（不留 v2）；GPU 口径设置内按引擎类型自定义；**GPU 低版本降级链补全（Win8~Win10 1607 走 D3DKMTQueryStatistics，仅 Win7 隐藏维度）**；停靠默认关闭、仅菜单入口；任务栏 item 首版提供；新增传感器数据调研章节（HWiNFO/PawnIO/LHM）；插件名定稿

---

## 0. 背景与目标

issue #19 中用户希望获得「同当前样式」的 **CPU Top 10 悬浮窗**，停靠在流速悬浮窗旁边。作者已回复将另起一个同形式插件。本方案将其扩展为五类资源维度的进程排行：

| 维度 | 排行依据 | 单位 |
|---|---|---|
| CPU | CPU 占用率 | % |
| 内存 | 专用提交内存（可选工作集） | MB/GB |
| 磁盘 IO | **文件读写速率（ETW FileIo 精确口径，不含网络）** | MB/s |
| GPU | 引擎利用率（口径按引擎类型自定义） | % |
| 显存 | 专用显存占用（可选+共享） | MB |

产品原则（继承 PNM）：

- 悬浮窗观感与 PNM 悬浮信息窗一致（亚克力/圆角/进程图标/右对齐数值/深浅主题自动）
- 零第三方依赖、`/MT` 静态 CRT、单 DLL 双架构（x64/x86）
- 自身开销目标：常驻 CPU < 1%、私有内存 < 10MB
- Win7 ~ Win11 全兼容（GPU 维度按系统版本降级；磁盘 IO ETW 档按权限/会话可用性降级并如实标注，见 §2.3）

## 1. 功能范围

### 1.1 核心功能

1. **排行悬浮窗**：显示某一指标的 Top N（默认 10，可配 5/10/15）进程列表。每行 = 进程图标 + 进程名 + 数值（右对齐，同 PNM 悬浮窗布局）。同名多进程（Chrome 等）默认合并为一行，可展开显示子进程（展开能力为 v2，见 §11）。
2. **指标集合**：CPU / 内存 / 磁盘 IO / GPU / 显存，共 5 个维度。磁盘 IO 可细分「读速率 / 写速率」两个子视图；显存可细分「专用 / 共享」。
3. **两种窗口模式**（详见 §6）：
   - 单窗切换模式：一个悬浮窗内通过滚轮/点击/快捷键切换当前显示的指标；
   - 多窗模式：自定义同时打开多个悬浮窗，每个窗口各自绑定一个指标、独立位置独立主题。
4. **窗口联动停靠**（详见 §7）：**默认独立浮动**；停靠（贴靠 PNM 详情窗 / TM 主悬浮窗并跟随移动）仅作为右键菜单选项提供，用户主动开启。
5. **任务栏显示项（首版提供，已拍板）**：一个 IPluginItem，在 TM 任务栏/主窗显示当前 CPU Top1 进程名 + 占用（形式同 PNM 的 Up/Down 两行项），点击切换悬浮窗显隐——TM 原生集成入口，复用 PNM 已验证的 item 交互模式。
6. **标题栏摘要**：悬浮窗头部显示该维度的系统总量（如 CPU 总占用、内存总量/已用、GPU 总占用、磁盘总读写速率）；可选叠加传感器读数（CPU/GPU 温度、CPU 频率，数据来自 TM 宿主，见 §2.7）。

### 1.2 明确不做（首版）

- 网络流量排行（PNM 的领域，不重复建设）
- 历史/趋势图（PNM 有完整 history 体系，本插件 v2 再评估）
- 结束进程等危险操作（首版仅「定位文件 / 属性」；PNM 有现成实现，v2 可搬）
- 传感器**丰富档**（风扇/电压/每核温度，见 §2.7 分层结论——首版仅取宿主已有的标量传感器）

## 2. 数据获取调研（Windows）

TrafficMonitor 及其插件宿主仅存在于 Windows，因此「不同平台」在本方案中落实为 **Windows 版本维度**（Win7/8/8.1/10/11、x86/x64/WOW64、WDDM 版本、有无独显、RDP 会话、管理员与否）。macOS/Linux 无对应宿主，不展开（等价物 `top`/`psutil`，仅备注）。

### 2.1 CPU —— 推荐单一快照法

**候选方案对比**：

| 方案 | API | 开销 | 限制 |
|---|---|---|---|
| **系统快照（推荐）** | `NtQuerySystemInformation(SystemProcessInformation)` | 一次调用返回全部进程，300 进程实测毫秒级（1~5ms） | ntdll 未公开 API，需动态取函数指针；结构体自行定义 |
| 逐进程句柄 | `OpenProcess` + `GetProcessTimes` | O(n) 次 OpenProcess，句柄开销大 | 受保护进程（杀软等）打开失败或数据缺失；短命进程易漏 |
| PDH 计数器 | `PdhOpenQuery("\Process(*)\% Processor Time")` | 首次枚举 + 每次 collect 数十 ms | 实例名撞名加后缀（#1/#2）需处理；最慢 |
| Toolhelp32 快照 | `CreateToolhelp32Snapshot` | 快 | 只有进程列表，**没有 CPU 时间**，需配合其他 API |

**推荐路线**：`NtQuerySystemInformation(SystemProcessInformation)`——任务管理器进程列表同源数据。一次调用同时拿到：

- 每进程 `KernelTime`/`UserTime`（CPU 时间，累计值）
- `ReadTransferCount`/`WriteTransferCount`/`OtherTransferCount`（IO 计数，降级口径用，见 §2.3）
- `WorkingSetSize`/`PrivatePageCount`（内存，见 §2.2）
- 进程名（ImageName，NT 路径）、PID、线程数、基优先级

**CPU% 计算**：`(ΔKernelTime + ΔUserTime) / (ΔwallTime × LogicalProcessorCount) × 100`，逻辑核数取 `GetLogicalProcessorInformation(Ex)`。CPU 时间是系统启动以来的累计值，天然免疫采样间隔抖动；首拍无差值显示 `--`。

**风险与对策**：

- **WOW64 结构对齐**：x86 插件跑在 x64 系统上时，wow64 层会返回 32 位视图的 `SYSTEM_PROCESS_INFORMATION`（`SYSTEM_THREAD::StartAddress` 为 `ULONG_PTR`），结构定义中所有指针宽度字段用 `ULONG_PTR` 并按 `NextEntryOffset` 步进即可（Process Hacker 同款处理，成熟方案）。x64 原生无此问题。PNM 的 win7_compat_check 双架构测试工具直接复用来验证。
- **未公开 API 稳定性**：该结构自 NT4 起稳定，任务管理器/Process Explorer/Process Hacker 全在用；仍按「尾部字段不解析」原则只读需要的字段，缓冲区按返回长度 `StatusInfoLengthMismatch` 递增重试分配（初始 512KB，翻倍增长）。
- **受保护进程**：快照中仍有 CPU 时间，ImageName 可能为空 → 显示 `<PID>`，与 PNM「进程名永不过期」策略一致做名字缓存兜底。
- **系统级空闲进程**：`Idle`/`System Idle Process` 不参与排行，但计入标题栏系统总量（100% − idle%）。

### 2.2 内存 —— 同一快照，零额外开销

`SYSTEM_PROCESS_INFORMATION` 中直接可取：

| 字段 | 口径 | 对应任务管理器列 |
|---|---|---|
| `PrivatePageCount` | 专用提交内存（**默认口径**） | 详细信息页「提交大小」 |
| `WorkingSetSize` | 工作集（含共享页） | 进程页「内存(活动的专用工作集)」的近似 |

- 排行默认按**专用提交**（更能反映进程真实负担，不受共享库重复计入影响）；设置中可切换工作集口径。
- 快照法拿不到「专用工作集」精确值（需 PSA 计数器），方案不追这个口径，设置页注明差异。
- 同名进程合并时内存直接求和（各进程独立地址空间，求和正确）。
- **瞬时值无 delta**，首拍即可显示——CPU/磁盘 IO 需要两拍，内存不需要，首拍体验更好。

### 2.3 磁盘 IO —— ETW FileIo 精确口径（首版主线，已拍板不留 v2）

**背景**：`GetProcessIoCounters` 及系统快照的 IO 计数统计的是进程**全部句柄 IO**（文件 + 网络 socket + 设备），**没有磁盘/网络拆分**（微软文档 + Microsoft Q&A 证实，任务管理器「磁盘」列同源同口径）。对「只关注磁盘 IO」的需求这是已知口径缺陷，不允许用标注遮掩——**首版即用 ETW 拿精确的文件读写口径**。

**候选方案对比**：

| 方案 | 数据源 | 口径 | 开销 | 限制 |
|---|---|---|---|---|
| IO 计数器差分 | 快照内嵌 `IO_COUNTERS` | 文件+socket+设备全混合 | 零（附带） | 无法拆分，仅作降级口径 |
| **ETW FileIo 事件（主线）** | 内核 `FileIo` 事件组（`FileIo/Read`、`FileIo/Write`） | **纯文件系统读写**，socket/设备 ioctl 不走文件系统事件 | 常驻消费线程，典型桌面每事件 ~100ns 手工解析 | 内核会话需管理员权限；Win7 会话唯一（见下） |
| ETW DiskIo 事件 | 物理磁盘栈 IRP | 真·物理盘流量 | 同上 | **事件不带 PID**，且缓存写回由 System(4) 的 lazy writer 发起，per-process 归属本质失真——业界（Process Explorer/资源监视器）均不用此口径 |
| PDH `Process\IO Data Bytes/sec` | 性能计数器 | 同 IO 计数器 | 低 | 同样不拆分，无增益 |

**主线设计：ETW FileIo/Read + FileIo/Write 事件**

- **事件结构**：内核经典事件（`EVENT_TRACE` 头含 `ProcessId`/`ThreadId`，内核事件头 PID 可靠），`FileIo_ReadWrite` payload 含 `TransferSize`。**手工按固定偏移解析，不走 TDH**——FileIo Read/Write 是布局最稳定的经典事件之一，TDH 逐事件 schema 查询（每事件几十 µs）在文件 IO 洪流下不可接受，手工解析每事件几十 ns（PNM etw_capture 用 TDH 是因为 TcpIp 事件 schema 复杂多变，此处不同）。
- **归属**：按事件头 `ProcessId` 累计读/写字节，天然精确到进程，含短命进程（事件流式到达，不依赖快照时机）。
- **口径语义**（设置页 tooltip 注明）：
  - 统计 `WriteFile`/`ReadFile` 级别的文件读写量——**含缓存命中**（写缓存未落盘也计入），与用户对「程序读写文件」的直觉一致；
  - **不含** socket 网络 IO、设备 ioctl、注册表 IO；
  - SMB/网络文件系统上的文件访问计入（文件系统栈的操作）；
  - 缓存写回落盘由 System 进程完成，不会虚增到用户进程（这正是放弃 DiskIo 口径的原因：物理盘 per-process 归属会因 lazy writer/预读严重失真）。
- **会话设计（关键，解决与 PNM 的共存）**：
  - PNM（同宿主进程的兄弟插件）已占用经典 **NT Kernel Logger** 会话消费 TcpIp/UdpIp；ETW 一个会话只允许一个消费者，附加它必然失败。
  - **解法：自建 `EVENT_TRACE_SYSTEM_LOGGER_MODE` 系统会话**（Win8+ 支持多个系统日志会话并存）：`StartTrace` 用独立会话名（如 `PTMFileIoSession`）+ 系统日志器模式 + 启用 `EVENT_TRACE_FLAG_FILE_IO` 关键字，与 PNM 的 NT Kernel Logger **互不冲突、互不干扰**（各自独立缓冲与消费）。
  - 只启用 FileIo 一个组（不启 DiskIo/映像加载/进程组等其余关键字），把事件面收到最小。
  - 缓冲参照 PNM 经验（120×256KB 量级起调，按丢事件计数调优）。
- **权限与降级链**（每一档如实可见，不静默冒充精确口径）：

  | 档位 | 条件 | 行为 |
  |---|---|---|
  | A 精确档 | Win8+ 且 TM 以管理员运行（或已提权） | 自建 system logger 会话，FileIo 精确口径 |
  | B 精确档（Win7） | Win7 且 NT Kernel Logger 空闲（PNM 未启用 ETW 等） | Win7 无多系统会话，只能用唯一的 NT Kernel Logger：空闲则自建启用 FileIo；被 PNM/其他工具占用则进 C 档 |
  | C 全口径档 | 无管理员权限 / Win7 会话被占 | 快照 IO 计数器差分（含网络），悬浮窗状态行**黄色警示**「IO 口径：全句柄（含网络）——需要管理员权限获取精确磁盘口径」，同 PNM 附加模式提示的交互模式 |

  档位在运行期重协商（TM 提权重启后自动升级到 A，参照 PNM ETW 智能降载/回退的状态机经验）。
- **开销控制**：
  - 消费独立线程（`ProcessTrace` 阻塞回调模型，PNM 同款）；回调内只做「PID 查表 + 字节累加」，无锁（线程私有 map，tick 线程定时 swap 走双缓冲，见 §5）；
  - 事件量级评估：典型桌面几百~几千事件/s（<1% 单核）；磁盘满载（复制大文件）数万事件/s，手工解析下采集线程 CPU 预算仍 <1%——**M1 验收含满载实测**（fastcopy/robocopy 场景记录插件 CPU 增量与丢事件数）；
  - 会话缓冲不足丢事件时按 ETW `EventsLost` 计数如实计入状态行，不假装完整。

### 2.4 GPU —— PDH 性能计数器主线（Win10 1709+），口径按引擎类型自定义

**候选方案对比**：

| 方案 | API/来源 | 最低版本 | 开销 | 限制 |
|---|---|---|---|---|
| **PDH GPU Engine（推荐）** | `\GPU Engine(*)\Utilization Percentage` | **Win10 1709** | 实例数 = 进程数×引擎数（数百~上千），单次 collect+格式化约 2~20ms，1s 一次可接受 | 实例路径字符串解析是主要成本；引擎并行求和可 >100% 需定口径（已拍板：设置内自定义） |
| D3DKMT 统计 | `D3DKMTQueryStatistics`（gdi32 动态加载，任务管理器同款） | Vista+（语义随 WDDM 演进） | 进程×适配器次内核调用 | 需枚举适配器 LUID；NodeRunningTime 为累计值需自行 delta；Win7/8 上 per-process 语义未验证 |
| NVML | nvml.dll | N 卡专属 | 低 | 仅 NVIDIA + 主要是 CUDA 进程，非通用，不做主线 |
| IGCL/ADLX | Intel/AMD SDK | 厂商专属 | — | 非通用、引入闭源依赖，违背零依赖原则，排除 |

**推荐路线**：PDH `GPU Engine` 计数器。

- 实例名格式 `pid_1234_luid_0x..._phys_0_eng_0_engtype_3D`：按 `pid_` 前缀解析 PID、`engtype_` 后缀解析引擎类型分组聚合 `Utilization Percentage`。
- **引擎类型口径（已拍板：设置内自定义多选）**：
  - 设置页「GPU 口径」= 引擎类型多选列表；列表**动态枚举**当前系统实际存在的 engtype 实例生成（不同 GPU/驱动暴露的引擎集不同——HWiNFO 里看到的「Video Encode 0/1」编号即同类型多实例，聚合时自动合并求和）；
  - 常见类型对照（显示名 ↔ PDH engtype 后缀）：

    | 显示名（中文界面） | engtype | 说明 |
    |---|---|---|
    | D3D | `3D` | 3D 渲染（任务管理器「3D」、HWiNFO「GPU D3D Usage」） |
    | 视频解码 | `VideoDecode` | 硬解 |
    | 视频编码 | `VideoEncode` | 硬编（含 0/1 多实例） |
    | 视频处理 | `VideoProcessing` | 后处理 |
    | VR | `VR` | 虚拟现实 |
    | 复制 | `Copy` | 引擎间搬运 |
    | 计算 | `Compute` | CUDA/OpenCL/DirectCompute |
    | 其他 | `Other`/系统出现的其余类型 | 动态发现 |

  - 预设：「全部引擎」（默认，求和上限 100%）、「仅 D3D」「仅计算」；多选任意组合时显示真实求和值，附带「超过 100% 截断」开关（默认开）；
  - 排行榜列头 tooltip 注明当前选中口径。
- 采样需要**两次 collect**（区间型计数器，`PdhGetFormattedCounter` 自动用两拍差值 cook），GPU 首拍显示 `--`。
- **PDH 查询单独建、单独降频**：与系统快照分开（默认 1s vs 500ms），关闭 GPU 相关窗口时整个 PDH 查询关闭（`PdhCloseQuery`），零残留开销。

**降级链（三级，逐档补全）**：

| 档位 | 系统范围 | 路线 | 说明 |
|---|---|---|---|
| **G1** | Win10 1709+ | PDH GPU Engine / GPU Process Memory | 上述主线路线 |
| **G2** | Win8 / 8.1 / Win10 1507~1607 | **D3DKMTQueryStatistics**（gdi32 动态加载，微软 DDI 官方文档最低 Windows 8） | GPU 利用率：`QueryProcessNode` → `NodeRunningTime`（累计值，相邻两拍 delta ÷ (dt × 节点数)）；显存：`QueryProcessAdapterMemory` → `BytesAllocated`（专用，共享细分在此档不可得）。枚举适配器拿 LUID 后按 进程×适配器×节点 查询，开销为每拍数百次内核调用（1s 频率下可接受）。**此档无 engtype 引擎命名**（node 只有编号）→ 引擎类型自定义口径降级为「全部节点求和」，界面如实标注 |
| **G3** | Win7 | 无可靠 per-process 路线 | WDDM 1.1 结构布局不同（老 `hAdapter` 句柄版），连任务管理器都从未提供 per-process GPU——**GPU/显存排行维度隐藏**；标题栏摘要仍显示**整机 GPU 利用率**（从 TM 宿主 `GetMonitorValue` 白拿，TM 的 LHM 采集在 Win7 可用），「摘要有值、排行注明系统不支持」 |

档位判定在运行期一次探测（PDH 计数器类别存在性 → D3DKMT 函数可取性 → 隐藏），RDP/无 GPU 场景按 G3 处理并显示原因。D3DKMT 结构在 SDK 头文件中不完整（官方文档确认），按 WDK 定义手工补齐，无新增链接依赖。NVML 路线已评估排除：仅 N 卡、仅覆盖 CUDA 进程、且无 per-process 利用率（只有 ComputeRunningProcesses 的显存），不通用。

### 2.5 显存 —— PDH GPU Process Memory（Win10 1709+）

- 计数器：`\GPU Process Memory(*)\Local Usage`（专用显存，新版本 build 名为 Dedicated Usage，按计数器类别名枚举两种都兼容）与 `Shared Usage`（共享系统内存）。
- 实例名同样以 `pid_N_...` 开头，解析逻辑与 GPU Engine 共用。
- 默认排行按**专用显存**；设置可切「专用+共享」合计视图。瞬时值，无需 delta。
- 多 GPU：默认合计，可按适配器分列（v2）。
- 降级链随 GPU 三级（§2.4）：G2 档用 `QueryProcessAdapterMemory` 的 `BytesAllocated`（专用口径，共享细分不可得）；G3 档隐藏。

### 2.6 汇总：采集矩阵

| 指标 | API | 版本/权限要求 | 默认频率 | 单次开销 | 首拍可用 |
|---|---|---|---|---|---|
| CPU | NtQuerySystemInformation 快照 | Win7+，普通权限 | 500ms | 1~5ms | 否（需两拍） |
| 内存 | 同上快照内字段 | Win7+，普通权限 | 随快照 | 0（附带） | **是** |
| 磁盘 IO | **ETW FileIo 事件流（主线）** | Win8+ **管理员**（Win7 需 NT Kernel Logger 空闲）；降级=IO 计数器 | 事件流常驻，500ms 汇总差分 | 满载数万事件/s，手工解析 <1% CPU | 否（需两拍） |
| GPU | G1 档 PDH GPU Engine；G2 档（Win8~Win10 1607）D3DKMTQueryStatistics | Win8+，普通权限 | 1000ms | G1 2~20ms；G2 数百次内核调用/拍 | 否（需两拍） |
| 显存 | G1 档 PDH GPU Process Memory；G2 档 QueryProcessAdapterMemory | Win8+，普通权限 | 随 GPU 查询 | G1 1~5ms；G2 随 GPU | **是** |
| 传感器摘要（可选） | TM 宿主 `GetMonitorValue`（见 §2.7 L0，**含 Win7 整机 GPU 利用率兜底**） | 随 TM | TM tick | 0 | 是 |

### 2.7 传感器数据调研（HWiNFO / PawnIO / LibreHardwareMonitor）

**问题**：能否用 HWiNFO 或 PawnIO 获取传感器数据（温度/频率/风扇等）？

**结论先行**：传感器是**整机级**数据（没有 per-process 温度/风扇），在本插件中只进悬浮窗标题栏摘要行，不参与排行。按成本分三层采用，首版只做 L0：

**PawnIO 定位澄清**：[PawnIO](https://pawnio.eu) 不是传感器数据接口，而是一个**签名的、可脚本化的通用内核驱动框架**——它被创造出来替代被 Windows Defender 拉黑的 WinRing0 驱动（CVE-2020-14979 等漏洞），[LibreHardwareMonitor 已把它集成为驱动后端](https://www.reddit.com/r/FanControl/comments/1nkes7v/v239)（FanControl v239+ 已随附，OpenRGB 也在跟进）。插件若直接对接 PawnIO 读写 MSR/IO 端口，等于要自己维护每代 CPU/GPU 芯片族的寄存器解读逻辑——这正是 LHM 数十万行代码在干的事，重复造轮子且不可维护。**结论：不直接用 PawnIO；用它的人（LHM/HWiNFO）已经在替我们干这活。**

| 层 | 来源 | 能拿到什么 | 成本 | 决策 |
|---|---|---|---|---|
| **L0 宿主白拿** | `ITrafficMonitor::GetMonitorValue`（TM 插件接口原生） | CPU/GPU 占用、CPU/GPU/硬盘/主板温度、CPU 频率、显存利用率等标量 | **零**——TM 已采集，函数调用即得 | **首版做**：标题栏摘要可选叠加温度/频率显示（设置开关，默认关） |
| **L1 LHM 嵌入** | 仿 TM 主程序 `OpenHardwareMonitorApi`（C++/CLI 包装 LibreHardwareMonitorLib，TM 源码自带全套参考实现：`GetHardwareInfo`、每盘/每核温度 map 等） | 全量传感器：每核温度、风扇转速、电压、功耗、每盘 SMART | 引入托管运行时（宿主 TM 已加载 CLR，增量可控）+ LHM DLL ~2MB + C++/CLI 包装层；驱动侧（WinRing0 已被拉黑/PawnIO 需用户装驱动）在无内核访问时传感器大量缺失 | v2 按需（若确有风扇/电压需求再做；届时参照 TM 现成代码） |
| **L2 HWiNFO 共享内存** | 用户安装 HWiNFO 并开启「Shared Memory Support」，插件读其共享内存段（Rainmeter 同款路线） | HWiNFO 全部传感器 | 零内核成本，但**强依赖用户装第三方软件**，违背零依赖原则 | v2 可选档（检测到 HWiNFO 共享内存存在时才出现在设置里） |

**推荐**：首版 L0（白拿宿主数据，摘要行可选显示温度/频率）；L1/L2 写入方案的远期章节，不进首版范围。

**线程模型**（继承 PNM 已验证模型）：

| 线程 | 职责 | 纪律 |
|---|---|---|
| TM 主线程 | 全部窗口消息循环与绘制、任务栏 item、选项对话框 | 窗口成员只有此线程可碰 |
| TimerQueue 定时器线程 | tick：快照采集 + PDH 查询 + 聚合排序 + 缓存替换 + PostMessage | `m_refresh_busy` CAS 防重入；不碰窗口成员 |
| ETW 消费线程（仅 A/B 档存在） | `ProcessTrace` 阻塞回调：PID 查表 + 字节累加（线程私有 map） | 回调内零系统调用零锁；tick 线程以双缓冲 swap 取走累计表 |

**关键设计决策**：

1. **单一数据管线服务全部窗口**：无论 1 窗还是 5 窗，采集只有一套；每拍产出「全部已启用指标的 Top N 结果表」，各窗口按绑定指标自取。多开窗口不增加采集成本（同指标共享）。
2. **按需启停采集维度**：collector 维护「被至少一个可见窗口绑定的指标集合」。GPU 系列无绑定时 PDH 全关；磁盘 IO 无绑定时 ETW 会话停止（A 档停会话零内核开销，重开有 ~10ms 会话建立成本，可接受）；全部窗口隐藏时定时器停，任务栏 item 降级为 TM tick 惰性取缓存。
3. **窗口类多实例化**：PNM 的 `s_instance` 单例改为 `HWND → CTopListWindow*`（`GWLP_USERDATA` + 静态注册表兜底），WndProc 静态分发。
4. **崩溃防护先行**：第一个窗口创建前防护机制就位（issue #7 教训不重演）。

## 5. 数据流设计

### 5.1 ETW 常驻流（磁盘 IO 主线，A/B 档）

```
内核 FileIo/Read+Write 事件
  → ETW 会话缓冲（PTMFileIoSession，独立于 PNM 的 NT Kernel Logger）
  → 消费线程 ProcessTrace 回调：
      pid = Header.ProcessId
      acc[pid].read  += Payload.TransferSize   (Read 事件)
      acc[pid].write += Payload.TransferSize   (Write 事件)
      （线程私有 unordered_map，无锁；高负载下 map 常驻热进程集合，~百项）
```

### 5.2 一拍采样周期（默认 500ms tick，GPU 每 2 tick）

```
TimerQueue 线程（RefreshTick，CAS 防重入）
 1. CheckLanguageChange()                          // 复用 PNM
 2. [每拍] NtQuerySystemInformation 快照
      ├ RawProc{pid, name, cpu_time, ws, private, io_counters(降级档用)}
      ├ delta → cpu%、（C 档时）io_read/write_Bps（计数器回退钳 0）
      └ 上拍状态整体替换
 3. [A/B 档] 与 ETW 消费线程 swap 累计表 → delta → disk_read/write_Bps
      ├ EventsLost>0 → 状态行如实标注丢失
      └ 短命进程：事件流里有 PID 但快照已无此进程 → 进程名缓存兜底，仍进排行
 4. [每 2 拍,若 GPU 已启用] PdhCollectQueryData ×2 → 按选中引擎类型聚合 GPU%、显存
 5. top_aggregator：同名合并、按指标排序、Top N 截取、（可选）EMA 平滑
 6. EnterCriticalSection(m_data_lock); m_snapshot = 整体替换; Leave
 7. 每个可见窗口 PostMessage(WM_PTM_REFRESH)
 8. 任务栏 item 从 m_snapshot 取（TM tick 时，不重复采集）
```

### 5.3 窗口侧（UI 线程）

```
WM_PTM_REFRESH:
 1. 锁内拷贝自己绑定指标的 TopRows（POD 行浅拷贝，微秒级）
 2. 脏检查：名单（PID 序列）+ 量化数值比对 → 未变直接 return（0 重绘）
 3. 有变化 → 重建 ULW 表面 + 图标 miss 入队；OnPaint 末尾 PumpIconExtraction(2)
```

## 6. 悬浮窗模式设计

### 6.1 窗口外观

复刻 PNM 悬浮信息窗：宽约 300px（DPI 自适应）、`WS_POPUP + WS_EX_TOPMOST + WS_EX_TOOLWINDOW`（常驻窗加 `WS_EX_APPWINDOW`，给任务栏按钮与最小化恢复入口——issue #18 教训）、亚克力/透明/模糊/不透明四档效果 + 不透明度滑条、圆角、深浅主题自动 + 文字反色。布局：

```
┌──────────────────────────┐
│ 磁盘 IO        ▾  [—][×] │  ← 标题栏：当前指标（点击弹指标菜单）
│ 总读写 128MB/s  45°C     │  ← 摘要行（系统总量 + 可选传感器）
│ 1 chrome.exe   32.4MB/s  │
│ 2 Code.exe     18.1MB/s  │  ← Top N 行：图标+名+数值（右对齐）
│ ...                       │
└──────────────────────────┘
```

### 6.2 单窗切换模式（默认）

- 滚轮循环切换 / 点击标题栏指标菜单 / 快捷键 `1~5`；切换只换读取的快照子集，**零额外采集零延迟**。
- 指标顺序：CPU → 内存 → 磁盘 IO → GPU → 显存（不可用维度灰显并标注原因）。

### 6.3 多窗模式

- 入口：标题栏右键 / 托盘菜单 / 选项对话框 →「新建悬浮窗」→ 选指标 → 新窗。
- 每窗独立：指标、位置、尺寸、主题档、透明效果；同指标可开第二窗（如「磁盘读」+「磁盘写」）。
- 上限 6 窗（每窗 ULW 表面 + 模糊层 ≈ 每窗 ~1.4MB 位图内存，6 窗可控）。
- 关闭语义：关单窗 = 移除该窗配置；关全部窗 = 退出悬浮窗模式（任务栏 item 保留可重开）。

### 6.4 持久化 schema（settings.json）

```json
{
  "refresh_ms": 500,
  "default_topn": 10,
  "memory_basis": "private",
  "gpu_engines": ["all"],           // "all" 或 engtype 列表 ["3D","VideoDecode",...]
  "gpu_cap_100": true,
  "io_view": "combined",            // combined | read | write
  "vram_basis": "dedicated",
  "sensor_summary": false,          // 标题栏传感器摘要（L0）
  "window_mode": "single",
  "windows": [
    { "metric": "cpu", "x": 100, "y": 100, "w": 300, "h": 420,
      "topn": 10, "docked": false, "dock_target": "auto" }

  "color_mode": 0, "popup_effect": 0, "popup_opacity": 100,
  "lang": "auto", "debug_logs": false

```

`docked` 默认 `false`（独立浮动），仅用户在菜单里开启停靠后为 `true`。运行期变更即时落盘（WM_EXITSIZEMOVE / 设置变更时机）。

## 7. 窗口联动停靠设计（默认关闭，菜单触发）

### 7.1 停靠目标与优先级

| 优先级 | 目标 | 检测方式 | 说明 |
|---|---|---|---|
| 1 | **PNM 详情窗**（类名前缀 `PNMDetail_`，标题 `ProcessNetMonitor`，常驻） | EnumWindows：类名前缀 + 属 TrafficMonitor.exe + 可见 | 最理想常驻锚 |
| 2 | **TM 主悬浮窗**（类名前缀 `TrafficMonitor`） | 复用 PNM `IsTMMainWindow` 判定（类名 + 与任务栏位置关系） | 无 PNM 详情窗时的锚 |
| 3 | PNM hover 悬浮窗（类名前缀 `PNMTooltip_`） | 同前缀法 | **不作锚**（秒级生命周期）；仅用于首显位置侧偏提示 |

### 7.2 停靠状态机（每窗独立，菜单入口）

```
[Floating 独立浮动] --右键菜单「停靠到…」--> [Docked 停靠跟随]
[Docked] --用户拖离(WM_EXITSIZEMOVE 后距锚>阈值)--> [Detached]
[Detached] --菜单「重新停靠」--> [Docked]
[Docked] --锚窗消失--> [Floating 冻结原位]（锚重现不自动吸回；菜单可手动重停）
```

- 默认停靠边：锚窗右侧垂直顶对齐，出屏翻左（工作区翻转逻辑复用）。
- 多窗排布：停靠态按创建序横向级联，一行满自动换行到锚窗下方。
- 全程**不主动**：不做「检测到锚窗就自动贴过去」——独立浮动是默认尊严，停靠永远是一次显式菜单动作的结果。

### 7.3 跟随机制：WinEventHook（跨进程的正确答案）

PNM 的子类化跟随只能同进程，对 PNM/TM 窗口跨进程不可用。替代：

- **主线**：`SetWinEventHook(EVENT_OBJECT_LOCATIONCHANGE, …, TrafficMonitorPID, 0, WINEVENT_OUTOFCONTEXT)` 按 PID 过滤，事件驱动、零轮询、系统原生跨进程。回调只记矩形 + PostMessage 重定位（回调内不做重活）。
- **跟随策略复用 PNM 三段式**：纯位移轻量 delta（`SetWindowPos` 同偏移）；尺寸/跨屏节流全量重定位（150ms）；`EVENT_SYSTEM_MOVESIZEEND` 强制终判。
- **兜底轮询**：500ms `GetWindowRect(锚)` 比对（钩子被干扰/漏事件时保底，失败可见不遮掩）。
- **生命周期**：仅存在 Docked 窗时挂 hook；全部脱离即 `UnhookWinEvent`。锚进程退出钩子自动失效，状态机回 Floating。

## 8. 性能设计（具体措施）

### 8.1 采集侧

1. **一拍三指标**：CPU/内存/IO 降级档共享一次快照；快照缓冲按需增长后**复用不释放**。
2. **频率分层**：快照 500ms（可配 250/500/1000/2000ms）；GPU PDH 1000ms 倍频分频；ETW 事件流常驻但每事件成本压到 ~100ns（手工偏移解析、无锁累计、PID 查表走热 map）。
3. **按需启停**：无 GPU 窗口 → PDH 全关；无磁盘 IO 窗口 → ETW 会话停止；全部窗口隐藏 → 定时器删；任务栏 item 单存时维持 TM tick 惰性取数。
4. **PDH 实例解析缓存**：「实例路径 → (pid, engtype)」映射缓存，实例集未变直接复用；只解析三个计数器。
5. **delta 钳制**：计数器回退（PID 复用/会话切换）差值钳 0，防下撑（PNM 同款防御）。

### 8.2 渲染侧

6. **脏检查跳过重绘**：Top N 名单与量化数值未变 → 不重建 ULW 表面不 Invalidate（静止画面零成本）。
7. **ULW 表面复用**：尺寸不变 DIB 不重建；三表面常驻复用。
8. **图标分帧提取**：绘制只查缓存，磁盘提取每帧 ≤2 个；按 exe 路径缓存天然去重。
9. **数值格式化缓存**：随脏检查一起比对，未变不重新格式化。

### 8.3 停靠/其他

10. WinEventHook 事件驱动无轮询常开；兜底轮询仅 Docked 态存在。
11. ETW 会话缓冲按丢事件计数调参；`EventsLost` 如实入状态行。

### 8.4 预算表（验收口径）

| 场景 | 目标 |
|---|---|
| 1 窗（CPU 单指标），500ms 拍 | 插件进程 CPU < 0.3%，私有内存 < 8MB |
| 5 窗全指标（ETW A 档 + GPU PDH 1s） | CPU < 1%，私有内存 < 12MB |
| 磁盘满载（robocopy 大文件）+ ETW A 档 | 采集线程 CPU 增量 < 1%，EventsLost = 0（缓冲调到够） |
| 全部窗口隐藏 | CPU ≈ 0%（定时器与 ETW 会话已停），内存 < 4MB |
| 静止画面（数据无变化） | 0 重绘 0 合成 |
| 拖动锚窗跟随（停靠开启时） | delta 路径 < 1ms/事件，无可感知掉队 |

验收工具复用项目模式：harness 程序 + 截图比对 + ETW 丢事件计数（tools/verify_* 的做法平移到新仓库）。

## 10. 兼容性与风险清单

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | Win8~Win10 1607 无 PDH GPU 计数器（Win10 1709 才引入） | 维度缺失 | **G2 档 D3DKMTQueryStatistics 路径补全**（§2.4 三级降级链，微软 DDI 最低 Win8，Process Explorer 同款技术）；仅 Win7 落 G3 隐藏维度 + 整机摘要兜底 |
| 2 | RDP / 无 GPU 下 GPU 计数器全 0 | 数据误导 | 「恒 0 且系统有 GPU」场景显示「远程会话不可用」提示（一次判定） |
| 3 | **ETW 需管理员；TM 未提权运行** | 磁盘 IO 落 C 档（全口径） | 状态行黄色警示 + 一键说明（PNM 附加模式同款交互）；TM 提权重启后自动升 A 档并消除提示 |
| 4 | **Win7 单内核会话与 PNM 冲突**（多系统会话是 Win8+） | Win7 + PNM ETW 开启时磁盘 IO 落 C 档 | 同 3，状态行如实标注「NT Kernel Logger 被 PNM/其他工具占用」；两者在 Win7 只能有一个吃内核会话，属系统限制非缺陷 |
| 5 | **FileIo 事件洪流（磁盘满载）** | 采集线程 CPU 高 | 手工偏移解析（无 TDH）+ 无锁累计 + 大缓冲；M1 满载实测验收（robocopy 场景）；极端持续满载下 EventsLost 如实显示 |
| 6 | **FileIo 含缓存命中**（写缓存未落盘也计） | 与「物理盘灯」观感差异 | 口径=文件读写量（业界通行：Process Explorer/资源监视器同口径）；设置 tooltip 说明；不追物理盘口径（per-process 不可靠，§2.3） |
| 7 | GPU 引擎求和 >100% | 数值超界 | 已拍板：引擎多选自定义 + 「超 100% 截断」开关默认开；口径入列头 tooltip |
| 8 | PDH 实例名格式 / D3DKMT 结构布局随 Windows 更新变化 | GPU 数据缺失或解析错乱 | PDH 解析宽松化（pid_/engtype_ 必配其余尽力）；D3DKMT 结构按 WDK 官方 DDI 定义手工补齐并带防御性长度校验；失败样本入调试日志 |
| 9 | WOW64 x86 结构对齐错误 | x86 版崩溃/乱数据 | `ULONG_PTR` + NextEntryOffset 步进；win7_compat_check 双架构用例覆盖 |
| 10 | 受保护进程（PPL）名字空 | 显示 `<PID>` | 进程名缓存兜底 + 首拍接受空名 |
| 11 | 短命进程闪现闪退导致排行跳动 | 观感 | 排行场景允许自然消失（瞬时视图语义）；EMA 平滑可选；短命进程有 IO/CPU 消耗时经事件流/名字缓存仍可见 |
| 12 | 跨进程跟随钩子被安全软件拦截 | 停靠跟随失效 | WinEventHook 为系统公开 API（放大镜同用）风险低；轮询兜底 |
| 13 | 锚窗类名变更/未装 PNM | 检测不到 | 停靠为可选功能，检测不到即菜单灰显，其余功能完整 |
| 14 | TM 宿主线程差异（1.85/1.86） | 初始化时序 | InitOnce 双入口（issue #12 教训复用） |
| 15 | DLL 卸载期窗口销毁崩溃 | 宿主崩溃 | g_shutting_down + SafeDestroyWindow + SEH（issue #7 方案复用）；ETW 消费线程在 DLL 卸载前有序 Stop（PNM 同款） |
| 16 | 多窗 + 亚克力多层表面显存占用 | 低配机负担 | 窗口上限 6；效果可整体降不透明 |
| 17 | ntdll 未公开结构未来变动 | 极端场景数据异常 | 只读头部稳定字段 + 防御性长度校验；异常显示采集失败而非崩溃 |
| 18 | 传感器 L0 依赖 TM 采集配置 | 摘要为空 | TM 未启用温度监控时摘要行自动隐藏该项（有值才显示） |

## 11. 实施阶段建议

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **M1 核心可用** | 插件骨架（接口/i18n/崩溃防护/构建）+ 快照路线（CPU/内存）+ **ETW FileIo 磁盘 IO（A/B/C 档位状态机）** + 单窗（每窗固定指标）+ 任务栏 item（CPU Top1）+ 设置持久化 | 与 Process Explorer 磁盘 IO 对照一致（±5%）；**robocopy 满载实测：插件 CPU < 1%、EventsLost=0**；C 档警示正确显示/消除；Win7/x64/x86 三环境跑通 |
